Put the vectors in a database

The first three modules searched vectors by hand. Here the same book goes into ChromaDB: 1,404 records with IDs, text and page metadata, queried through a database API. The point is to see which layer a framework owns.

Worked example — one question, two retrieval paths

The trace asks the same question as module 01 and compares the from-scratch hybrid retriever with Chroma's default vector-store path. It shows a stored entry, the query result, the ranking difference and a metadata filter. Each step is expandable.

05_chroma_store

Source: 05_chroma_store.py (expand) 
"""See a chunk become a record in a vector database.

Step 1: state the question and the two retrieval paths being compared.
Step 2: load the chunks and open the persistent Chroma collection.
Step 3: inspect one chunk as a stored record with vector and metadata.
Step 4: query Chroma with its own default embedding, not our saved vectors.
Step 5: compare the result with the from-scratch hybrid retriever.
Step 6: filter by metadata and state where this demo stops.

Run from the repo root:
    .venv/bin/python demos/05_chroma_store.py > demos/05_chroma_store.txt

This is the code path behind `python -m rag.cli capstone --tool chroma`.
No chat model is called. All numbers print at 2 decimals.

The captured .txt shows a first run that builds the collection. Later runs
reuse the persistent store, so the "entries before" line will differ.
"""

import sys
from pathlib import Path

sys.path.insert(0, str(Path(__file__).resolve().parent.parent))

import chromadb

from rag.chunk import load_chunks
from rag.config import Settings
from rag.retrieve import Retriever

QUESTION = "Where was the bodhisatta born?"


settings = Settings.load()
dense_files = sorted(settings.index_dir.glob("dense-*.npy"))
if not dense_files:
    raise RuntimeError("No dense index found; run ingest --embed-backend fastembed")
backend = dense_files[0].stem.removeprefix("dense-").split("-")[0]
settings = settings.overrides(embed_backend=backend)

print("== step 1: two retrieval paths ==")
print(f"  question: {QUESTION}")
print(f"  path A: rag/retrieve.py hybrid — TF-IDF + {backend} bge-small vectors")
print("  path B: Chroma vector store — Chroma's own default embedding")
print("  Path B does not load our saved .npy or .joblib files.")

chunks = load_chunks(settings)
client = chromadb.PersistentClient(path=str(settings.data_dir / "chroma"))
collection = client.get_or_create_collection(
    name="noble_warrior", metadata={"hnsw:space": "cosine"}
)
print("\n== step 2: the persistent collection ==")
print(f"  chunks in book: {len(chunks)}")
print(f"  collection: {collection.name} | entries before: {collection.count()}")
print(f"  persisted at: {(settings.data_dir / 'chroma').relative_to(settings.data_dir.parent)}")
if collection.count() == 0:
    collection.add(
        ids=[chunk.id for chunk in chunks],
        documents=[chunk.text for chunk in chunks],
        metadatas=[
            {
                "chapter": chunk.chapter,
                "section": chunk.section,
                "page_start": chunk.page_start,
                "page_end": chunk.page_end,
            }
            for chunk in chunks
        ],
    )
print(f"  entries after: {collection.count()}")

result = collection.query(query_texts=[QUESTION], n_results=4)
top_ids = result["ids"][0]
distances = result["distances"]
result_metadatas = result["metadatas"]
assert distances is not None and result_metadatas is not None
record = collection.get(
    ids=[top_ids[0]], include=["metadatas", "documents", "embeddings"]
)
print("\n== step 3: one chunk as a database entry ==")
print(f"  id: {record['ids'][0]}")
metadatas = record["metadatas"]
embeddings = record["embeddings"]
documents = record["documents"]
assert isinstance(metadatas, list) and metadatas and isinstance(metadatas[0], dict)
assert embeddings is not None and len(embeddings) > 0
assert isinstance(documents, list) and documents and isinstance(documents[0], str)
record_metadata = dict(sorted(metadatas[0].items()))
print(f"  metadata: {record_metadata}")
print(f"  vector dimensions: {len(embeddings[0])}")
print(f"  text: {' '.join(documents[0].split())[:140]}...")
print("  An entry is id + vector + text + metadata, not just a row of numbers.")

print("\n== step 4: query the vector store ==")
print("  Chroma embeds the question with its own default model and searches by cosine distance.")
print("  rank  id       distance  chapter")
for rank, (chunk_id, distance, metadata) in enumerate(
    zip(top_ids, distances[0], result_metadatas[0]), start=1
):
    print(f"  {rank:>2}.   {chunk_id:<7} {distance:.2f}      {metadata['chapter']}")

retriever = Retriever(settings, chunks=chunks)
ours = retriever.search(QUESTION, k=4, mode="hybrid")
print("\n== step 5: compare with the from-scratch retriever ==")
print("  rank  Chroma   distance  |  ours     fused  lexical  dense")
ours_by_rank = {rank: item for rank, item in enumerate(ours, start=1)}
for rank in range(1, 5):
    item = ours_by_rank[rank]
    print(
        f"  {rank:>2}.   {top_ids[rank - 1]:<7} {distances[0][rank - 1]:.2f}      |  "
        f"{item.chunk.id:<7} {item.score:.2f}     {item.lexical:.2f}     {item.dense:.2f}"
    )
overlap = set(top_ids) & {item.chunk.id for item in ours}
print(f"  overlapping ids: {len(overlap)} of 4")
print("  Three things changed at once: store, embedding model and score type.")
print("  A difference here is not evidence that a vector store improves recall.")

filtered = collection.query(
    query_texts=[QUESTION], n_results=3, where={"chapter": "Birth"}
)
filtered_distances = filtered["distances"]
assert filtered_distances is not None
print("\n== step 6: metadata filtering and boundary ==")
print("  Entries carry chapter metadata, so filtering is a database query:")
for rank, (chunk_id, distance) in enumerate(
    zip(filtered["ids"][0], filtered_distances[0]), start=1
):
    print(f"  {rank}. {chunk_id} distance={distance:.2f} chapter=Birth")
print("  No LLM is called here. This demo stops at retrieved records;")
print("  rag/llm.py and rag/generate.py perform the answer step separately.")

What Chroma actually owns

Chroma stores records: an ID, a vector, the original text and metadata such as chapter, section and page range. It persists them under data/chroma/, builds a cosine HNSW index and answers collection.query(...). It does not decide how the book was cleaned, how chunks were cut, how lexical and dense scores are fused, or how a prompt is built. Those remain the app's own code.

The demo prints one complete entry so the abstract phrase "a chunk is a record" becomes concrete: c0030, a 384-value vector, the chapter Birth, pages 16–17, and the passage text.

Why the ranking moved

Chroma's results were c0030, c0032, c0023 and c0024, with cosine distances 0.35, 0.35, 0.36 and 0.39. Our hybrid retriever returned c0030, c0032, c0023 and c0031 — three of four overlap. Three things changed at once: the storage system, the embedding model and the scoring method. Chroma uses its own default embedding here, not the bge-small vectors from module 03, and it performs dense vector search only rather than lexical/dense fusion. A difference in the list is therefore not evidence that a vector database improves recall.

What is actually gained

At 1,404 chunks there is no speed or accuracy win: the old np.dot plus argsort is already instant. What changes is the architecture — persistence across processes, first-class metadata that can be filtered in the query, an index that will scale to a much larger corpus, and a portable API. The demo's final query uses where={"chapter": "Birth"} to show that filtering is now a database operation.

This is stage 7 of the README's learning path, the capstone: the same pipeline expressed with a real framework so you can compare it against chunk.py and retrieve.py. No LLM is called on this page; the answer step lives in rag/generate.py and rag/llm.py.

Questions that came up while learning this

These are the questions asked while discussing vector stores and frameworks. Open one to read the explanation.

What is the difference between a vector store and a document/chunk/index/query-engine?

A vector store is one component: records of id + vector + text + metadata that answer "give me the k nearest vectors". In rag/capstone.py:30-50 a Chroma collection does exactly that, and this demo uses the same calls.

Document, chunk, index and query-engine are the pipeline vocabulary of a framework such as LlamaIndex. A Document or Node wraps a chunk with metadata; an Index builds a searchable structure over those nodes; a QueryEngine takes a question, retrieves, builds a prompt, calls an LLM and returns an answer with sources (capstone.py:106-122). The vector store is a part; the query engine is the end-to-end workflow that may use one.

What is meant by a vector database? Is a chunk an entry? Is our 1404 x 27246 matrix a vector database? Is embedding a vector-DB representation?

A vector database persists vectors with metadata and does nearest-neighbour search, usually with an ANN index and a query API. One chunk can be one record. Here c0030 carries its vector, text, chapter, section and page range — step 3 of the trace prints that record.

lexical.joblib (1404 × 27,246) and dense-*.npy (1404 × 384) are vector representations — the data a vector DB would store — but they are not a database: no named records, metadata store, ANN index or query layer. Search there is hand-written dot product and argsort. Embedding produces coordinates suitable for a vector database; the database is the system around them. The book is represented by the collection of chunk vectors, not one book vector.

Do ChromaDB and LlamaIndex come together, or are they different technologies with the same purpose?

Different layers. Chroma is a vector database: storage and similarity search, stopping at retrieval. LlamaIndex is an orchestration framework: documents, nodes, index, query engine and LLM wiring, and it can use many vector stores.

In rag/capstone.py they are two separate demos. chroma_demo() uses Chroma alone with no LLM; llamaindex_demo() uses LlamaIndex with its default in-memory store plus Ollama, with no Chroma. They could be combined by giving LlamaIndex a Chroma-backed vector store, but that is not what the current code does. Analogy: catalogue and shelves versus librarian and reading desk.

So what will be the improvement?

At 1,404 chunks, none in accuracy. With the same vectors and cosine distance the top-k results are effectively identical, and brute-force dot product is already instant. The real gains are structural: persistence in data/chroma/, first-class records with metadata and filters, an HNSW index that scales beyond this small corpus, and a portable API.

Nothing here improves recall, MRR, citation rate or groundedness — those come from chunking, the embedding model, fusion, the prompt and the LLM. A vector store is plumbing around the vectors. This demo also uses Chroma's own default embedding rather than bge-small, so differences in the ranking come from the model swap as well as the store.
