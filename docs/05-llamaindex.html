Let a framework run the pipeline

The first four modules built each gear by hand. LlamaIndex replaces the wiring: documents, an index and a query engine take a question all the way to an answer. This page shows what stays the same underneath and what the framework actually takes over.

Worked example — one question through a query engine

The trace wraps the same 1,404 chunks as LlamaIndex Documents, builds a vector index with our local embedding adapter, retrieves nodes without an LLM, then asks the query engine for an answer. The last step is live; its output is a snapshot. Each step is expandable.

06_llamaindex_engine

Source: 06_llamaindex_engine.py (expand) 
"""See LlamaIndex wrap retrieval and generation into one query engine.

Step 1: state the question, the local model and the embedding adapter.
Step 2: turn the same chunks into LlamaIndex Documents with metadata.
Step 3: build a VectorStoreIndex using our local fastembed adapter.
Step 4: retrieve nodes without calling the LLM.
Step 5: ask the query engine, which retrieves, prompts and calls Ollama.
Step 6: name what the framework replaced and where the boundary is.

Run from the repo root:
    .venv/bin/python demos/06_llamaindex_engine.py > demos/06_llamaindex_engine.txt

This is the code path behind `python -m rag.cli capstone --tool llamaindex`.
The step 5 answer is a snapshot: LlamaIndex does not use this repo's response
cache, so a rerun can produce different wording. All numbers print at 2 decimals.
"""

import sys
from pathlib import Path

sys.path.insert(0, str(Path(__file__).resolve().parent.parent))

from llama_index.core import Document, VectorStoreIndex
from llama_index.core import Settings as LISettings
from llama_index.llms.ollama import Ollama

from rag.capstone import _local_embedder_class
from rag.chunk import load_chunks
from rag.config import Settings

QUESTION = "Where was the bodhisatta born?"


settings = Settings.load()
print("== step 1: question and wiring ==")
print(f"  question: {QUESTION}")
print(f"  generation: {settings.llm_backend} / {settings.llm_model}")
print(f"  embedding: {settings.embed_model}, through the capstone adapter")
print("  thinking: off, to keep the local model's output bounded")

chunks = load_chunks(settings)
documents = [
    Document(
        text=chunk.text,
        metadata={
            "chapter": chunk.chapter,
            "section": chunk.section,
            "page": chunk.page_start,
        },
    )
    for chunk in chunks
]
first = documents[0]
print("\n== step 2: chunks become Documents ==")
print(f"  Documents: {len(documents)} from {len(chunks)} chunks")
print(f"  first metadata: {first.metadata}")
print(f"  first text: {' '.join(first.text.split())[:110]}...")

Embedder = _local_embedder_class()
LISettings.embed_model = Embedder(model_name=settings.embed_model)
LISettings.llm = Ollama(
    model=settings.llm_model,
    request_timeout=settings.request_timeout,
    thinking=False,
    additional_kwargs={"num_predict": 500},
)
index = VectorStoreIndex.from_documents(documents)
print("\n== step 3: build the index ==")
print(f"  index type: {type(index).__name__}")
print("  VectorStoreIndex embedded every Document with the local adapter.")

engine = index.as_query_engine(similarity_top_k=4)
nodes = engine.retrieve(QUESTION)
print("\n== step 4: retrieve without an LLM call ==")
print("  rank  score  page  chapter")
for rank, item in enumerate(nodes, start=1):
    assert item.score is not None
    node = item.node
    print(
        f"  {rank:>2}.   {item.score:.2f}   {node.metadata['page']:>3}  "
        f"{node.metadata['chapter']}"
    )

print("\n== step 5: query the engine (live local call) ==")
response = engine.query(QUESTION)
print(f"  answer: {' '.join(str(response).split())}")
print("  This line is a captured snapshot, not a reproducible score.")

print("\n== step 6: what the framework owns ==")
print("  Document + Index + QueryEngine replaced our chunk/index/prompt/LLM wiring.")
print("  The vector model is still ours; the LLM is still Ollama.")
print("  Unlike rag/llm.py, this path has no response cache; no answer is reused.")

What the framework took over

Our own path in module 01 is a chain of explicit calls: load_chunks(), Retriever.search(), format_context(), llm.chat(). LlamaIndex packages that chain as Document → VectorStoreIndex → QueryEngine. You give it documents and an embedding function; the engine embeds the question, retrieves, builds a prompt, calls the LLM and returns an answer with sources.

Two things did not change: the vectors still come from our fastembed adapter over bge-small-en-v1.5, and generation still goes to Ollama. LlamaIndex owns the orchestration, not the model. The adapter is only about fifteen lines in rag/capstone.py, which is why the framework could be used without replacing the embedding stack.

Three views of the same book

Module 01's hybrid retriever returned c0030, c0032, c0023 and c0031 by fusing lexical and dense scores. Module 04's Chroma collection, using Chroma's own default embedding, returned c0030, c0032, c0023 and c0024 with cosine distances 0.35, 0.35, 0.36 and 0.39. Here LlamaIndex retrieves pages 14, 17, 15 and 14 in the Birth chapter with scores 0.81, 0.75, 0.73 and 0.73. The first three chunks recur because the underlying text and the question are the same; the ordering differs because the embedding model and scoring rules differ.

Notice also what the answer is not. Our own generate.py prompt demands one citation per sentence and an explicit "I don't know" when evidence is absent. The query engine uses its own default prompt, so its answer quotes source passages but does not follow that strict contract. A framework saves wiring; it does not inherit your teaching rules automatically.

The capstone, complete

Chroma answered "where do the vectors live and how are they searched?" LlamaIndex answers "how do I turn documents and a question into an answer?" The from-scratch code in chunk.py, index.py, retrieve.py, generate.py and llm.py answers both by showing every step. That comparison is stage 7 of the README's learning path: not a different RAG system, but the same system expressed at three levels of abstraction.

The step 5 answer is a captured snapshot. LlamaIndex does not use this repo's response cache, so running the demo again may produce different wording even with thinking off.
