Compose the pipeline with LangChain

LlamaIndex packages the pipeline as a query engine. LangChain packages it as runnables you chain together. This page asks whether that changes the answer — and uses one missing chunk to show how much retrieval depth matters.

Worked example — one question, two context sizes

Same question as every other module. The trace wraps the 1,404 chunks as LangChain Documents, builds a Chroma store with our bge-small adapter, retrieves with a LangChain retriever, then runs the same LCEL chain twice: once with four excerpts and once with twelve. Both answers are live snapshots, not reproducible scores. Each step is expandable.

What LCEL actually buys you

Instead of one QueryEngine object, LangChain gives you pieces that compose with |: a prompt template, a chat model and an output parser. The retriever is another swappable piece. That is the real lesson here — not a new retrieval algorithm, but a different way to wire the same parts.

Two details matter in the trace. The embedding model is still ours, wrapped in a ten-line Embeddings adapter; Chroma is only the store. And ChatOllama needs reasoning=False, not think=False, or a thinking model spends its whole token budget and returns empty content. This demo uses qwen2.5:3b because lfm3 returned empty content under the strict prompt; the output says so explicitly.

Follow-up questions

But the bodhisatta was born in Lumbini — does the book actually say that?

Yes. The only chunk containing "Lumbini" is c0035 in the Birth chapter on page 19. It says the bodhisatta "has been born for welfare & happiness in the human world in a town in the Sakyan countryside, Lumbini."

The from-scratch hybrid retriever ranks that chunk 12 of 12 in a twelve-result list. LangChain's dense-only Chroma retriever ranks it 9 of 12, with distance 0.69. Neither puts it in the top four used for the first answer. With four excerpts the model correctly refuses: "I don't know based on the book." With twelve excerpts the same chain answers: "The bodhisatta was born in Lumbini, a town in the Sakyan countryside..."

So this is a retrieval-depth failure first, not a generation failure. The question contains no word "Lumbini", so lexical matching cannot find it. The dense score is reasonable but not high enough to beat chunks about the mother's womb and the birth scene. The generator can only use what the retriever hands it: widening the context from four to twelve changed the answer without changing the prompt, model or chain.

Why use qwen here when the default is lfm3?

Because the strict prompt produced empty content from lfm3:latest through langchain-ollama, even with reasoning=False. A spike showed that think=False is silently accepted and ignored by that wrapper. This is a framework-integration observation, not a claim that lfm3 is a worse retriever or reasoner. The demo prints the substituted model in step 1 and marks both answers as snapshots.

Is LangChain better than LlamaIndex?

Neither is "better" at retrieving this book. LlamaIndex gives you a query engine; LangChain gives you composable runnables and a retriever interface you can point at different stores. If you want agents, tools or callbacks, LangChain is the more natural place to go next. If you want one object that takes documents to an answer, LlamaIndex is shorter. Both leave the vectors and the LLM underneath unchanged, which is why modules 04 through 07 keep returning the same neighbourhood of chunks.
